## 1. Context and Problem Statement

ReSecure is a zero-trust, local-first cybersecurity utility engineered to detect file corruption, verify cryptographic integrity, and mathematically recover damaged digital assets. In enterprise environments, digital files face persistent degradation vectors: silent bit rot on magnetic/flash storage, deliberate ransomware header destruction ("intermittent encryption"), in-transit byte drops across untrusted networks, and unexpected I/O terminations.

Designing the system requires resolving four fundamental technical and philosophical challenges:
1. **Mathematical Certainty vs. Probabilistic Synthesis**: Should file recovery employ generative AI / LLM synthesis to "hallucinate" missing content, or deterministic Forward Error Correction (FEC)?
2. **Tamper Evident Metadata vs. Plain Checksums**: How do we prevent adversaries from forging checksum manifests to conceal malicious payload modifications?
3. **Data Privacy, Chain of Custody & Zero Telemetry**: How do we guarantee that evidentiary files and sensitive enterprise assets are never leaked to external networks or altered during forensic inspection?
4. **Technology Stack Selection**: What programming languages, framework ecosystems, and library runtimes provide high performance, zero runtime memory bloat, native binary manipulation, and rapid developer velocity across frontend and backend?

---

## 2. Decision Drivers

- **Zero Tolerance for Hallucinated Data**: In cybersecurity, digital forensics, and compliance, recovering an altered or pseudo-plausible file is strictly worse than declaring it unrecoverable. Recovered files must be bit-for-bit identical to original states.
- **Strict Non-Destructive Operations**: Source files are evidentiary artifacts. In-place writes or mutations violate forensic chain of custody.
- **Tamper Resistance**: Checksums stored in plain text can be regenerated by an attacker; manifests must be cryptographically authenticated.
- **Resource Predictability**: Chunked streaming must bound memory consumption ($RSS \le 150$ MB) regardless of file size up to 2.0 GB.
- **Local Sovereignty**: Zero external network dependencies, telemetry pings, or cloud API calls.
- **Decoupled Multi-Agent Factory Ergonomics**: Formal contracts (OpenAPI 3.1, SQLite DDL, TypeScript definitions) to unblock parallel work by Database, UI/UX, Backend, QA, and Security agents.

---

## 3. Considered Options

### Option 1: Generative AI / LLM File Repair
- Use large language models or diffusion/inpainting models to fill in missing bytes or corrupted rows.
- *Pros*: Can generate plausible-looking data even with zero parity files.
- *Cons*: Mathematically indeterministic; generates synthetic hallucinations that fail cryptographic hash verification; completely unacceptable in security and forensic contexts; requires GPU/cloud dependencies.

### Option 2: Pure Checksums (MD5 / SHA-256) + Mirrored Backups
- Compute file-level hashes and restore from full secondary mirror copies.
- *Pros*: Simple to implement.
- *Cons*: 100% to 200% storage overhead; zero algorithmic error-correcting capability when a backup block is damaged.

### Option 3: Galois Field $GF(2^8)$ Reed-Solomon Codec + HMAC Manifests + Local Python/React Stack (Chosen)
- Partition files into fixed 64KB chunks, generate byte-striped Reed-Solomon parity blocks ($M = \lceil K \times R\% \rceil$), authenticate manifests using HMAC-SHA256, and enforce bit-for-bit SHA-256 validation before recovery commit.
- Implement Core & API in Python 3.13 (FastAPI, `reedsolo`, Pillow, SQLite) and UI in React 18 (TypeScript, Vite, Tailwind CSS).

---

## 4. Decision Outcome

We select **Option 3: Deterministic Reed-Solomon Forward Error Correction over Galois Field $GF(2^8)$ with HMAC-SHA256 Manifest Authentication and Local-Only Execution**.

### 4.1 Technology Stack Architecture

| Layer | Selected Technology | Architectural Justification |
| :--- | :--- | :--- |
| **Backend Core & API** | **Python 3.13 + FastAPI** | Native byte manipulation, high-performance async I/O, Pydantic v2 data validation, OpenAPI auto-generation, rich standard library (`hashlib`, `hmac`, `struct`, `sqlite3`). |

### 4.2 Architectural Tenets & Justifications

#### 1. Deterministic Reed-Solomon Priority over Generative AI
In cybersecurity and data preservation:
- Generative AI produces plausible but mathematically corrupt data. A single bit discrepancy invalidates cryptographic hash chains, digital signatures, and database pointer integrity.
- Reed-Solomon provides proven forward error correction: $K$ data blocks with $M$ parity blocks can mathematically reconstruct any $M$ missing or corrupted blocks with zero guesswork.
- Recovery is only declared successful (`VERIFIED_EXACT`) if the reconstructed file's SHA-256 matches the pristine root hash bit-for-bit.
- If damage exceeds parity ($E_{\text{damaged}} > M$), ReSecure executes a **Safe Failure Protocol**: it refuses to write an unverified file, issues Exit Code 3, and provides diagnostic metrics.

#### 2. Tamper-Evident HMAC-SHA256 Manifests
- Checksum manifests stored in plain JSON or text files can be modified by an attacker (e.g. ransomware modifying a file and regenerating the plaintext manifest hash to conceal its intrusion).
- ReSecure mandates HMAC-SHA256 authentication:
  - Manifest contents are serialized into canonical JSON (lexicographically sorted keys, compact separators).
  - The HMAC signature is computed using a pre-shared secret key or local vault key.
  - Verification validates the HMAC signature before inspecting file chunks. Any tampering triggers an immediate fail-closed security halt (Exit Code 2).

#### 3. Strict Non-Destructive Operations
- Source files are opened strictly in read-only mode (`O_RDONLY` / `FileShare.Read`).
- The recovery engine strictly prohibits `source_path == output_path`. Recovered files are written to user-designated destinations.
- Atomic file commits: Data is written to staging files in the destination directory, verified against root SHA-256, and atomically renamed (`os.replace`) only after root SHA-256 validation passes.

#### 4. Bounded Memory Streaming Architecture
- To prevent Out-Of-Memory (OOM) denial-of-service on large files (up to 2.0 GB), the engine streams files in fixed 64KB chunks ($S_c = 65,536$ bytes).
- Parity generation and erasure decoding stripe across chunks byte-by-byte, bounding memory consumption to $O(S_c \times M)$ ($RSS \le 150$ MB).

#### 5. Sovereign & Air-Gapped Local-First Architecture
- All cryptographic hashing, parity matrix math, and format validation run entirely in local user space.
- Zero network requests, zero dynamic telemetry, zero remote telemetry tracking.

## 5. Consequences

### Positive
- **Provable Bit-for-Bit Integrity**: Cryptographic invariance guarantees reconstructed files are authentic replicas of pre-incident files.
- **Fail-Safe Honesty**: Security analysts are never misled by corrupted files disguised as recovered.
- **Tamper Resistance**: Manifest forgery attacks are defeated by HMAC-SHA256 authentication.
- **Forensic Admissibility**: Non-destructive operations preserve original evidence and chain of custody.
- **Lightweight Footprint**: Embedded SQLite and local FastAPI eliminate cloud infrastructure costs and external services.

### Negative / Trade-offs
- **Storage Overhead**: Reed-Solomon parity requires additional storage proportional to configured redundancy (e.g., 20% redundancy on a 1 GB file requires 200 MB of parity data).
- **Parity Threshold Limit**: Exact recovery is mathematically impossible if damage exceeds available parity shards ($E > M$).
- **Heuristic Repair Limitations**: When falling back to heuristic structural repair, content is mutated to achieve syntax compliance, which cannot guarantee semantic business completeness (mitigated by explicit `.repaired` naming and JSON disclosure logging).
